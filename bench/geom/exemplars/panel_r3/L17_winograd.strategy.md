# L17_winograd — strategy record

Geometry `L = 17` (17³ = 4913 complex doubles per volume). File
`impl/L17_winograd.c`, `fft3d_name() == "L17_winograd"`.

---

## Round 1 (first round; assignment: "a hand-derived 17-point module — does it beat Rader?")

**Headline.** Yes, but not for the reason the minimum-multiplication literature
says. The Winograd/WFTA programme (minimise multiplies, pay in adds) loses on
this hardware, exactly as `docs/literature/02 §3.3` predicts. What *does* win is
one level of the **cyclic → (cyclic ⊕ negacyclic) halving with sign-only
reductions**, applied to the *symmetrised* Rader convolution. That gives a
**296-instruction** 17-point complex DFT — 12% below the 336-instruction dense
conjugate-symmetric kernel that FFTW's `FFTW_EXHAUSTIVE` planner selects for
n=17, and 24% below Rader-17's 388 — while staying within 4% of Rader's flop
count. Measured against the dense kernel in an otherwise byte-identical harness:
**32.3 µs vs 39.4 µs per 17³ transform, −18%.**

### 1. Derivation (reproducible; the checks are in the numbers below)

Write `w = exp(-2πi/17)`, `P = 17`, `g = 3` (a primitive root mod 17).

**(a) Symmetrise.** Pairing `j` with `17-j`,

```
X[k] = x0 + Σ_{j=1..8} [ c_jk · u_j  −  i · s_jk · v_j ],
u_j = x_j + x_{17-j},  v_j = x_j − x_{17-j},
c_jk = cos(2π jk/17),  s_jk = sin(2π jk/17)
```

and `X[17-k]` is the same with `s → −s`. This is FFTW's `dft/generic.c` form:
8 conjugate pairs × 8 inner steps × 4 FMA = 256 FMA + 80 add = **336 instr**.

**(b) The group structure that FFTW does not use.** `(Z/17)*` is cyclic of order
16; its quotient by `{±1}` is cyclic of order **8**, generated by the image of
`g = 3`. Index `j` and `k` by that quotient:

```
m, n = 0..7 ;  folded[m] = |3^m mod 17| folded into 1..8 = [1,3,8,7,4,5,2,6]
                sigma[m] = sign, i.e. 3^m ≡ sigma[m]·folded[m]  = [+,+,−,−,−,+,−,−]
```

Then, **exactly** (verified numerically, max err 2.4e-15 / 1.4e-15):

```
cos(2π folded[m]·folded[n] /17) =  c[(m+n) mod 8]              (CIRCULANT)
sin(2π folded[m]·folded[n] /17) =  sigma[m]·sigma[n]·(−1)^⌊(m+n)/8⌋ · s[(m+n) mod 8]
                                                                (NEGACYCLIC, up to
                                                                 diagonal signs)
c[r] = cos(2π·3^r/17),  s[r] = sin(2π·3^r/17)
```

This is the canonical Rader statement `Z[x]/(x^16−1) = Z[x]/(x^8−1) ⊕
Z[x]/(x^8+1)`: `u` feeds the length-8 **cyclic** correlation with the **real**
kernel `2cos`, `v` feeds the length-8 **negacyclic** correlation with the
**imaginary** kernel `−2i·sin`. Both diagonal sign matrices are free — one folds
into the order of the subtraction that forms `v`, the other into which of
`X[k]`, `X[17−k]` gets the `+`.

**(c) The win: halve the cyclic side with sign-only reductions.** `x^8−1 =
(x^4−1)(x^4+1)`, so with `P_m = u_m + u_{m+4}`, `Q_m = u_m − u_{m+4}` (m=0..3)
and `cp(t) = (c(t)+c(t+4))/2`, `cm(t) = (c(t)−c(t+4))/2`:

```
A(n) = x0 + Σ_{m=0..3} cp((m+n) mod 4) · P_m          n = 0..3   (cyclic-4)
B(n) =      Σ_{m=0..3} ±cm((m+n) mod 4) · Q_m         n = 0..3   (negacyclic-4)
C_n = A(n) + B(n),   C_{n+4} = A(n) − B(n)
```

because `cp` has period 4 and `cm` is antiperiodic with period 4. Cost per real
component: 8 adds (P,Q) + 16 + 16 MACs + 8 adds = 48, against 64 for the direct
8×8 apply. Seeding `A(n)` with `x0` makes the DC addition free for all eight
`C_n`, and `X[0] = x0 + Σ_{m=0..3} P_m` (4 complex adds, not 8).

**(d) The negacyclic half is left dense — on purpose.** `x^8+1` is irreducible
over ℚ *and over ℝ up to √2*, so it admits no sign-only halving. Every route was
counted (see "what did not work"); all lose.

**(e) Exact instruction count** (per 17-point complex transform; counted in the
emitted assembly, not estimated):

| stage | instructions |
|---|---|
| `u_m, u_{m+4}` (8 complex adds) | 16 |
| `v_m` incl. sigma (8 complex subs) | 16 |
| `P_m, Q_m` | 16 |
| `X[0] = x0 + ΣP` | 8 |
| `A(n)`, n=0..3, x0-seeded | 32 FMA |
| `B(n)`, n=0..3 | 32 FMA |
| `C_n = A±B` | 16 |
| `S̃_n = Σ_m ŝ(m+n) ṽ_m`, n=0..7 (dense negacyclic-8) | 128 FMA |
| output combine, 8 conjugate pairs × 4 | 32 |
| **total** | **192 FMA + 104 add = 296 instr, 488 flops** |

Confirmed by `grep -cE "vfmadd|vaddpd|vsubpd|vmulpd"` on `pass2_a4` /
`pass2_a8`: **296** in both, of which 168 are `vfmadd` and 24 are `vmulpd`
(chain heads that had no addend to fuse). Per volume: `3·289·296 = 256 632`
FP instructions, 423 096 flops.

Comparison table, same accounting as `literature/02 §2.4–2.7`:

### 2. Layout, index mapping, SIMD

One pass = "transform the outer index of a `[17][289]` array, store with the
index order rotated left":

```
in[x][y][z] --P1--> A[y][z][kx] --P2--> B[z][kx][ky] --P3--> out[kx][ky][kz]
```

so the transformed axis is always the outer one (stride `SP`) and the 289-long
spectator pair is always **contiguous**. Lanes hold `W` consecutive spectators
⇒ every lane executes identical straight-line code with lane-invariant
broadcast constants, and there is **no cross-lane traffic inside the kernel** —
which is precisely the vectorisation that FFTW and MKL do not have at n=17
(`literature/02 §6.1`: FFTW's AVX2 speedup at 17³ is 1.00×).

* **Split re/im**, so ×(±i) is a register rename plus a sign folded into the
  next add — the negacyclic kernel is all ×(i·real), so this is worth having.
  Pass 1 de-interleaves on load (2 shuffles per 2 loads), pass 3 re-interleaves
  on store.
* **The tail.** `289 = 36·8+1 = 72·4+1`: exactly one spectator per pass,
  `(q,r) = (16,16)`, is not in a vector group. It is done by a *scalar*
  instantiation of the same kernel macro. No masking, no padding-lane waste
  (which would have been 41% at W=8 if 17 z-values had been the lane axis), and
  no out-of-bounds read past the last volume.
* **Padding.** Spectator stride `SP = 296` (= 8·37) so all 17 source rows are
  64-B aligned. The 17 rows land in L1 sets `37a mod 64`, all distinct.
* **Store side.** The rotation is paid inside the store: 17 output vectors
  (lanes = old spectator) → `W` lane-major runs of 17 contiguous doubles, via
  `W·log2 W` two-source shuffles per `W×W` block (24 per block at W=8:
  `vunpckpd` / `vpermt2pd` / `vshuff64x2`). The `W` lanes' destinations are
  adjacent, so together they write one contiguous 136·W-byte block — the store
  stream is sequential. Shuffles sit on port 5 while the FMAs are on port 0(/1),
  so on a **1-FMA-unit** SKX/CLX part they are free.
* **Scratch** = 2 buffers × split re/im × 17 × SP doubles = **161 kB**,
  L2-resident on the target (1 MB L2), independent of `B`. B=1 and B=2048 run
  the identical code path and get within 20% of the same per-transform time.
* **Runtime autotune** over 4 bit-identical variants ({256-bit, 512-bit} ×
  {two register-blockings of the A/B stage}) in `fft3d_create()`. All four
  execute the same arithmetic in the same order, verified with `cmp` on the
  output files, so the choice cannot change the answer. This exists because
  **AVX-512 is not obviously the right width here**: Xeon Gold 5218 is a
  Gold-52xx, i.e. a **single-AVX-512-FMA-unit** part, so a 512-bit FMA and two
  256-bit FMAs have *identical* peak FP throughput (8 doubles/cycle) while the
  512-bit path additionally pays the licence-2 frequency (`literature/04 §8.2`:
  Gold 5120 measured 2.3 GHz under AVX2 vs **1.6 GHz** under AVX-512).
  512-bit's real advantage here is that it halves the *non-FP* work per lane
  (loads 270 vs 337, stores 154 vs 124-per-half-the-lanes, shuffles 96 vs 132
  per 8 lanes) — see "next".

### 3. What was measured

**Machine: Haswell Xeon E5-2680 v3, 2.5 GHz, AVX2 only, no AVX-512**, gcc 11.4,
`-O3 -march=native -mtune=native -std=gnu11`, shared interactive node (11 other
implementers benchmarking concurrently → ±5–15% run-to-run; `min` over samples
is the stable statistic). **The 512-bit variants cannot be executed here**; they
compile and are verified correct via GCC's 2×ymm emulation of `vector_size(64)`,
and their AVX-512 code generation was inspected under
`-mavx512f -mavx512dq -mavx512vl -mtune=cascadelake`.

Best of 3 independent processes, 20 samples each (the leaderboard's statistic):

| case | per transform | GF/s (5N log2 N) | rel_l2 vs numpy |
|---|---|---|---|
| B=1 | **32.18 µs** | 9.4 | 3.24e-16 |
| B=8 | 32.90 µs | 9.2 | 3.26e-16 |
| B=64 | 32.77 µs | 9.2 | 3.26e-16 |
| B=256 | 37.97 µs | 7.9 | 3.26e-16 |
| B=2048 | 39.33 µs | 7.7 | 3.26e-16 |

The B≥256 step is the in/out buffers leaving L3 (256 volumes × 78.6 kB × 2
buffers = 40 MB): the transform itself is batch-independent, only the streaming
of `in` and `out` changes. `-Wall` is clean.

Reference on the *same* Haswell node from `literature/02 §1`: FFTW 3.3.10
patient 17³ = **103.1 µs**, i.e. this is **3.2× faster than FFTW** at B=1 with
AVX2 only. Repeatability: 2nd and 3rd `fft3d_execute` on one plan are
bit-identical to the 1st; `in` is unmodified. All four variants produce
byte-identical output files.

**Per-group cost decomposition** (W=4, one spectator group of 4 lanes, from
`pass2` in isolation, 2.5 GHz):

| what | cycles/group |
|---|---|
| loads+stores only, no kernel, linear store | 103 |
| + kernel (296 FP ops) | 211 |
| + transposed store instead of linear | **315** |
| FP-throughput floor (296 ÷ 2 per cycle) | 148 |

and from the assembly, per group: 296 FP, **337** load-port µops (of which 224
are the `.LC` constant operands of the FMAs), 124 stores, 66 shuffles. So at
W=4 on AVX2 the *load port* (169 cycles) is the binding resource, not FP, and
the phases barely overlap (600+ µops per group is ~3× the ROB).

**Kernel comparison in situ** (identical harness, only the 17-point module
swapped; `-DL17_DENSE_KERNEL` builds the dense one, it is left in the file):

| kernel | FP instr/group | load µops/group | B=1 time |
|---|---|---|---|
| this nested module | 296 | 337 | **32.3 µs** |
| dense conj-symmetric (= FFTW's choice) | 336 | 490 | 39.4 µs |

−18%, more than the −12% instruction delta, because the split also cuts the
MAC count *and* the constant-operand loads (the 8×8 cos apply needs 64 distinct
constants per component; the 4×4 pair needs 8).

### 4. What was tried and did NOT work — with the number that killed it

1. **Full Winograd / WFTA-17 (the assignment's nominal target).** Rejected on
   counts, not on vibes. Published: 70 mul + 314 add = **384 instructions**
   (Burrus T7.1) or 82 + 274 = **356** (T7.2) versus **296** here and **336**
   for FFTW's dense kernel. The multiplication saving is real (70 vs 192 MACs)
   and worthless: add, mul and FMA all have the same throughput on the same
   ports from Haswell on, and Winograd's `C·D·B` shape cannot fuse a multiply
   into an add, so every saved multiply costs ≥ 2 adds. **Winograd-17 is 30%
   more instructions than this module.** This is the well-evidenced negative
   result the assignment asked for.
2. **Winograd cyclotomic length-8 cyclic convolution** for the `u` half
   (`x^8−1 = (x−1)(x+1)(x²+1)(x⁴+1)`, 14 multiplies). Hand-counted: 24 adds to
   reduce + 3 mul/4 add for the `x²+1` factor + 9 mul/~15 add for `x⁴+1` +
   ~20 adds to recombine ≈ **14 mul + 63 add per real component = 154
   instructions for complex data**, against **128** for the direct 8×8 and
   **96** for the sign-only halving actually used. Loses to both.
3. **Splitting the negacyclic half**, three ways, all losing (per complex
   vector, against 128 for dense):
   * √2 factorisation `x^8+1 = (x^4−√2x²+1)(x^4+√2x²+1)`: 4 mul + 16 add to
     reduce (the two reductions share the √2 products), 32 MACs, ~16 add to
     recombine = 68/component → **136**.
   * `x^8+1 = (x^4−i)(x^4+i)` over ℂ, where ×(±i) is free: the reduction *is*
     free but the kernel becomes complex, so each MAC costs 4 real ops instead
     of 2 → 16 + 128 + 16 = **160**.
   * Odd-DFT diagonalisation (2 × ODFT8 + 8 complex pointwise) ≈ **200**.
   * Even/odd split with Karatsuba (3 negacyclic-4 products) = 48 MAC + ~16 add
     per component = **128** — exactly a tie, with a worse dependency graph.
   Conclusion: `x^8+1` at length 8 is a hard floor. It is 128 of the 296.
4. **A second level on the cyclic-4 part.** `cyclic-4 → cyclic-2 ⊕
   negacyclic-2` costs 4 + 8 + 4 = **16** per component versus **16** direct.
   Exactly break-even; not done.
5. **Making the lane axis `z` (the contiguous axis) instead of a flattened
   spectator pair.** 17 lanes' worth of work in ⌈17/8⌉ = 3 vector groups is
   **41% wasted lanes** at W=8 (18% at W=4). The 289-long flattened spectator
   wastes 2.4% (one scalar transform per pass) and costs the in-register
   rotation instead. Kept the flattened spectator.
6. **Hoisting the 23 distinct kernel constants into registers.** A wrong-result
   probe that collapses all S-stage constants to one value (so gcc keeps it in a
   register) drops the load count 337 → 201 and the time 316 → **257
   cyc/group, −19%** — so the prize is real. But: at W=4 there are only 16 ymm
   registers, and gcc *rematerialises* (re-loads) rather than keeping values
   live. Two schedules aimed at this both failed to reduce loads at all:
   * t-ordered (Hankel anti-diagonal, so one constant serves 4–8 FMAs) with
     2×4 tiles, 13 live values: loads 337 → **344** (worse), 33.4 µs vs 32.3.
   * same with 4×8 tiles (all 8 `v` pairs held): loads → **374**, 34.2 µs.
     Under AVX-512 codegen (32 registers) the same schedules give 281/279 loads
     against schedule-a's **270** — still no better. Dropped both; only the
     A/B-fusion schedule was kept as an autotune candidate (264 vs 270 loads at
     512-bit, i.e. noise).
7. **Prefetching** the next group's 34 source lines: +2 groups ahead 336
   cyc/group, +4 → 345, +8 → 352, source+dest → 338, against **329** with none.
   Uniformly *worse*: the pass is L2-bandwidth-bound, not latency-bound, and 34
   extra µops per group is pure cost.
8. **Software pipelining.** Double-buffering the loads: 376 cyc/group vs 315
   (worse — extra stack traffic). Double-buffering the *stores* (defer the
   transpose one group): 305 vs 315, i.e. 3% and inside the noise. Not adopted.
9. **Padding sweep** for `SP` ∈ {296, 304, 312, 320, 328, 344, 360}: 32.7–36.8
   µs with no structure beyond the ±10% node noise. 17 is odd, so as
   `literature/04 §7.3` says, cache geometry at L=17 is free. Kept SP = 296
   (the smallest multiple of 8, chosen for alignment, not for conflicts).
10. **Breaking 4K aliasing** by staggering the four scratch arrays onto
    different 4 KiB phases: 318 vs 311 cyc/group. No effect.
11. **Unrolling the transposed-store block loop** by hand: 321 vs 310. No
    effect (gcc already unrolls the inner two levels).
12. **Compilers.** gcc 11.4 / 12 / 13.2 / 16.1 all land at 32.1–33.2 µs; `-O2`
    is catastrophic (60 µs — the straight-line kernel needs `-O3`'s scheduling);
    `-fno-tree-vectorize` and `--param=max-completely-peeled-insns=2000` are
    neutral. **No compiler request needed**; the default gcc with the panel's
    flags is fine.
13. **Batch-in-the-lanes** (the layout `literature/02 §8.7` recommends) was
    costed and rejected: it removes all in-pass shuffles but needs a pack and an
    unpack that are themselves transposes of *complex* data, ≈ 2·7370 = 14 700
    shuffles/volume against ≈ 14 500 for the three in-pass rotations, plus it
    raises the working set W-fold (629 kB at W=4) and only works for B ≥ W,
    while the current code path is identical for B=1 and B=2048. Not worth a
    second implementation for ≤ 5%.

### 5. Next (in the order I would do them)

1. **The store port and the constant loads are the two remaining walls**, and
   both are halved per-lane by 512-bit code, which is why the autotuner exists.
   The first thing to do with the monitor's numbers is read off which variant it
   picked and how far apart 256-bit and 512-bit landed. **No AVX-512 measurement
   for this kernel exists anywhere yet** (corpus gap 6); that number is the
   single most valuable output of this entry.
2. **Constant residency, done properly.** The probe says −19% is on the table at
   W=4 and gcc will not get there by itself. The way to force it is intrinsics
   plus explicit `register` discipline, or emitting the S stage as an
   anti-diagonal sweep in *inline asm* / with `__builtin_ia32_*` so the 15
   distinct `ŝ(t)` live in 15 zmm across the whole group loop (32 registers make
   this feasible at 512-bit: 15 constants + 8 accumulators + 8 data + temps).
   Expected 10–15% on top.
3. **Fuse passes 2 and 3 over `kx`-blocks** to remove one buffer's worth of L2
   traffic (−33% of the 472 kB/volume). The dependency works out (pass 3 needs
   all `z` for a set of `kx`, pass 2 produces exactly that), but `17 = 8+8+1`
   makes the last block one lane wide; needs a 9-wide or ragged block scheme,
   worth ~5% and fiddly.
4. **Non-temporal stores in pass 3 for large B.** At B=2048 the per-transform
   time rises 32.5 → 39.7 µs; the output write is 1/3 of the DRAM traffic purely
   as read-for-ownership. Pass 3's per-group destination is one contiguous
   136·W-byte block, so full-line NT stores are possible when the block start is
   64-B aligned (it is iff `q + r0 ≡ 0 mod 4`) — a partially-NT store path.
5. **Try the 128-MAC negacyclic-8 as 3 negacyclic-4 Karatsuba products** (item
   3 above, the exact tie). It is a tie on instruction count but replaces 128
   FMAs with 96 MACs + 32 adds; if the machine turns out to be FMA-port-bound
   rather than instruction-bound (i.e. if the Gold 5218 really has one FMA unit
   but two ports able to take adds), it becomes a win. Cheap to test once a
   real AVX-512 measurement exists.

## Round panel_r2 (2026-08-21)

Node standings going in (panel_r1): this entry 18.259 µs at B=1 (2nd, behind
L17_matrixsimd 16.880), 20.532 at B=8 (1st), 26.737 at B=256 and 30.586 at
B=2048 (behind L17_rader's 25.984 / 27.863). Development moved to wallaby
(Sapphire Rapids, full AVX-512, 2 FMA units) — the first round in which the
512-bit variants could actually be *run* during development. Caveat on every
number below: wallaby was shared with the other panel_r2 implementers this
round, so run-to-run sd swung between 0.04% and 33%; min across repeated runs
is the only statistic used.

### What changed (three things, all in the same file)

1. **Kernel variant C (c4/c8) — the register-residency fix for round 1's
   constant-load wall** (round 1 "did not work" item 6: −19% was on the table
   but gcc rematerialises). The fused A/B first half is kernel B's, unchanged.
   The negacyclic S stage becomes ONE sweep over the 8 v-pairs into 16
   accumulators (all 8 outputs at once) instead of two 4-output sweeps, and
   the 8 distinct sine constants are broadcast once per *pass*, then made
   opaque with an empty `asm("" : "+v"(C0), ...)` so gcc can neither fold them
   back into per-FMA `.LC` memory operands nor rematerialise the broadcasts.
   Sweep liveness: 16 accumulators + 8 constants + 2 data = 26 vectors — fits
   the 32-register EVEX file (node, wallaby), guaranteed spills on a 16-register
   AVX2 file (guarded: the asm is only emitted under `__AVX512F__ && __AVX512VL__`).
   **Bit-identical to kernels A/B by construction**: same accumulation order
   over m, and `acc − v*C` (vfnmadd) rounds identically to `acc + v*(−C)`.
   Static counts (gcc 11.4, `-march=sapphirerapids`), per pass2 instantiation:

   | variant | total instr | mem loads | rip-relative (.LC) loads |
   |---|---|---|---|
   | b4 | 796 | 246 | 164 |
   | **c4** | 813 | **178** | **72** |
   | b8 | 998 | 284 | 142 |
   | **c8** | 1016 | **238** | **74** |

   So the S-stage constant traffic is gone (the remaining 72 are the first
   half's 8 cyclic constants × rotations). This matters most where the load
   ports are the binding resource: the *node's* 256-bit path (2 FMA ports, so
   FP floor 148 cyc/group vs measured-in-round-1 load pressure 169). On
   wallaby, which is FP-bound at both widths, c8 vs b8 was 9.69 vs 9.85 µs at
   B=1 — a small real win; c4 was **bimodal (13.3 / 22.9 / 25.8 µs)** — see
   "did not work".

2. **Stage-2 plan-time tuning in the batched regime** (borrowed wholesale from
   `L17_matrixsimd`'s record, items 11–12 and its stage-2 design). When
   `batch >= 64`, `fft3d_create()` re-tunes all 6 variants × {prefetch on,off}
   on a working set of up to 384 volumes = 60 MB in+out — past L3 on the node
   (22 MB) *and* on wallaby (60 MB) — timed in consecutive blocks per
   candidate, never interleaved (matrixsimd measured interleaved A/B
   mis-ranking by 35% on the node; blocked tuning agreed with the driver to
   0.5%). This fixed a real failure: the round-1 tuner timed a single
   L2-resident volume and its pick was both wrong for the streaming regime and
   fragile under contention — one wallaby B=256 run before the change measured
   21.6 µs/transform from a bad pick; after the change the same case is 11.4.
   Setup cost grows to ~0.4–0.9 s at large batch; setup is unscored.

3. **Cross-volume input prefetch as a tunable candidate.** During pass 2 —
   which touches no DRAM at all (both its buffers are L2-resident scratch) —
   each group issues 17 (W=4) or 34 (W=8) `prefetcht1` for the *next* volume's
   input, covering 1224 of its 1229 lines, gated on a pointer that is NULL for
   the last volume and at B=1 (zero cost there). Round 1's prefetch failure
   (item 7) was *same-volume* prefetch on Haswell into an L2-bandwidth-bound
   pass; this is different — it overlaps next-volume DRAM latency with a pure-
   compute pass. Measured on wallaby at B=2048 with variant forced to c8:
   **47.53 ms (pf on) vs 49.70 ms (pf off), −4.4%** in the true streaming
   regime; neutral at B=256 (in+out still fits wallaby's L3). The stage-2
   tuner decides per machine; prefetching cannot change results.

   Also: `fft3d_description()` now reports the picked variant and prefetch
   flag (e.g. "var=c8, pf=1"), so the next leaderboard carries back what the
   node's tuner chose — round 1's biggest open question about this entry.

round trip* — citing L36_pfa's 1.89× from removing a cache-level round trip.
That is what was built.

### What changed: two fused-pass-2+3 variants, f4 (256-bit) and f8 (512-bit)

The three-pass structure had pass 2 write a full-volume B scratch
(2×17×289×8 ≈ 78.6 KB split re/im) that pass 3 then read back with SP-strided
accesses — ~157 KB of L2 round-trip traffic per volume that exists only to
carry the (z,kx,ky) rotation between passes. The fused variants delete it:

1. **Pass 1 stores A in a kx-blocked spectator order** (w = vector width):
   `(y,z,kx) → y*SP + (kx/w)*(17w) + z*w + kx%w` for kx<16, and the kx=16
   plane to a separate tail region at `y*SP + 272 + z`. Since pass 1's
   transposed store is table-driven anyway (per-lane base offsets), this
   relayout is **free** — same store count, different int32 tables (`b8f/b4f/
   tf`), plus a chunk stride of 17w instead of w in the tst variants (tst8f/
   tst4f). 272 = 2·136 = 4·68 works for both widths.
2. **Passes 2+3 then complete one kx-block at a time.** Per block: 17 pass-2
   groups (lanes = kx-in-block, loads `A[y*SP + blk*17w + z*w]` — all aligned,
   which is why the relayout exists; the natural s = z*17+kx order would have
   made every fused load split cache lines) write a `[17 z][w*17 (kx,ky)]`
   mini-buffer via the ordinary tst transpose (bases `z*17w + j*17`), then 17
   pass-3 groups (lanes = consecutive (kx,ky) spectators, loads
   `Bblk[z*17w + w*h]`, again aligned since 17w ≡ 0 mod w) read it straight
   back and store interleaved into `out` (bases = block-local `bo` table +
   `2*kx0*289` pointer offset). Mini-buffer size: **18.5 KB at w=4, 37 KB at
   w=8** (re+im) — L1-resident on wallaby (48 KB), L1-scale on the node
   (32 KB; f8's spills a little into L2, f4's fits).
3. **The kx=16 tail is its own 1-wide block**, vectorised over z (pass 2) and
   over ky (pass 3) through a tiny 17×24-padded buffer (24 keeps both v8 and
   v4 loads aligned). Scalar-kernel count per volume is unchanged at 3
   (pass-1 (y,z)=(16,16); pass-2 z=16; pass-3 ky=16), and the vector group
   count is unchanged at 108 (w=8): the fusion moves **no arithmetic and no
   µops — only cache traffic**.

Kernel schedules inside the fused variants: f8 uses kernel C (register-
resident sine constants; the node's own B=1 pick last round), f4 uses kernel
B (round 2 showed c4 bimodal under gcc's allocator; not retried, per the
record). Same kernels, same per-element accumulation order ⇒ the fused
variants are **bit-identical** to a/b/c — confirmed by identical rel_l2 AND
rel_max digits across all forced variants on identical inputs (3.269e-16 /
3.725e-16 at B=1), each bit-repeatable across executes. The tuner's choice
still cannot change the answer.

Tuner: stage 1 and the batched stage-2 tuner now range over **8 variants**
{a4,a8,b4,b8,c4,c8,f4,f8} × {pf on,off}; `fft3d_description()` reports the
pick (vn table extended), so the next leaderboard again carries the node's
choices back. Cross-volume input prefetch is preserved inside the fused
pass-2 loops (36 lines/iteration × 34 iterations = 1224 of 1229 lines at w=8;
18×68 at w=4), still a tunable that cannot change results.

### What was tried and did NOT work / what to know

1. **Nothing failed outright this round** — the fusion is a straight win at
   both widths on wallaby. But calibrate: the gain is ~6%, not L36_pfa's 89%,
   because the deleted round trip here was already L2-resident (157 KB), not
   the 830 KB L3/DRAM slab L36 deleted. The VERDICT's suspicion that my ~5%
   estimate "is probably low" was itself slightly low: 6% on a machine whose
   L2 is 2 MB. **On the node (1 MB L2, and measured not-FP-bound) it should
   transfer at least fully; that is the number to read next.**
2. **Do not fuse passes 1+2 instead and expect more.** Costed while designing:
   either fusion deletes exactly one full-volume buffer; fuse(2,3) is the
   right one because its mini-buffer is written AND read inside one block
   (L1), while fuse(1,2)'s block output would still be the full B scratch.
   Fusing all three is impossible in this structure — pass 3 needs all z for
   a (kx,ky), so one full-volume intermediate is irreducible.
3. **The kx-blocked A relayout is what makes the fusion free.** A first sketch
   kept A's natural s = z*17+kx order and had fused pass 2 load at
   `z*17 + kx0` — unaligned, and at w=8 nearly every load splits a cache
   line. The blocked layout costs nothing (table-driven stores) and makes
   every fused load and store vector-aligned. Anyone repeating this move at
   another size: relayout the producer, don't eat split loads in the consumer.
4. f8's mini-buffer (37 KB) exceeds the node's 32 KB L1d; f4's (18.5 KB) fits.
   If the node's tuner picks f4 in cells where wallaby picks f8, that is the
   reason — it is a capacity effect, not a licence effect, this time.
