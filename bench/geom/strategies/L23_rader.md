# L23_rader — strategy record

First implementation for this geometry (round panel_r6).  The stub that created this
entry asked one question: *was the panel's L=17 win about primes being easy for us, or
about 17 being a lucky prime?*  This round answers it with operation counts and a
measurement, and ships a competitive implementation.

## Round panel_r6 (2026-08-21)

### The answer to the round's question, up front

**17 was lucky.**  The panel's prime-length advantage over the libraries survives at
p = 23 (we are 6–8× ahead of MKL/FFTW on wallaby), but it does NOT come from Rader —
it comes from the conjugate-folded direct form, which works at any small length.  At
p = 17 Rader added real savings on top of the fold because p−1 = 16 = 2^4; at p = 23,
p−1 = 22 = 2·11 and Rader adds exactly nothing.  The counts:

* Rader-23 maps k ≠ 0 outputs to a length-22 cyclic convolution (g = 5, primitive
  root mod 23).  Since g^11 ≡ −1 (mod 23), the ±fold splits conv-22 into a cyclic-11
  correlation with REAL kernel cos(2π·5^q/23) acting on u_j = x_j + x_{23−j}, plus a
  cyclic-11 correlation with real kernel sin(2π·5^q/23) acting on w_j = −i(x_j −
  x_{23−j}).  **This is identical, up to the Rader index permutation, to the
  conjugate-pair fold of the dense DFT matrix** (FFTW's dft-generic form, what
  L23_matrixsimd does).  The permutation buys nothing for direct evaluation — the
  circulant structure only matters if you can convolve in fewer ops.
* At 17, you could: x^16 − 1 = (x−1)(x+1)(x²+1)(x⁴+1)(x⁸+1) is a sign-only
  factorization all the way down, so every CRT split costs only additions
  (L17_winograd's cyclic/negacyclic module, adopted by L17_rader in r2: 296 FP
  instructions vs 336 dense-folded, −12%).
* At 23 the quotient group has odd prime order 11 and x^11 − 1 = (x−1)·Φ₁₁(x) with
  Φ₁₁ irreducible over Q.  The only free split is the (x−1) component (the conv DC),
  which the folded form already gets via the k=0 row.  Below the 121 fused FMAs of a
  direct 11-circulant matvec, every known realization trades fused FMAs for unfused
  additions and LOSES on FMA hardware, where one FMA = one add = one FP-port cycle:
  - **Winograd/CRT minimal conv-11**: 20 real mults (1 for (x−1), 19 minimal for the
    deg-10 product mod Φ₁₁) but the Φ₁₁ pre/post addition networks cost well over
    130 adds per convolution.  Per line (two convolutions on complex data): ≥ ~300
    unfused vector ops against 242 fused FMAs direct.  Loses ~25% before its deep,
    serial add chains are even priced.
  - **Karatsuba linear conv 11 = 6+5** (wrap for cyclic): M(11) = M(6)+M(6)+M(5) =
    18+18+15 = 51 mults + ~150 adds ≈ 200 ops per convolution vs 121 fused.  Loses.
  - **Classic Rader via FFT-22** (2 × [Good–Thomas 2×11 with Winograd DFT-11
    modules: ~40 mult + 168 add complex each] + 22 pointwise complex mults): ≈ 2×
    the vector-op count of the folded direct form.  Loses badly.  This is the same
    conclusion L17_rader r1 reached for its FFT-16 route relative to the fold-based
    module, now with a worse constant because 11 has no radix structure.

So the honest optimal Rader-23 IS the folded direct form, and this entry implements
it as well as I could.  L23_matrixsimd arrived at the same arithmetic from the dense
side (its header explicitly deferred the "Winograd cyclic-11" experiment; consider it
done by counting: don't implement it, it cannot win on this port model).  FFTW's own
documented hedge that direct multiplication wins "for small ones, like 17-23"
(LITERATURE.md §2) is confirmed measured at 23.

### Technique (as implemented)

Row-column 3D: one folded 23-point kernel per axis, SIMD lanes = WC adjacent
independent lines (WC = 4 zmm / 2 ymm, gcc vector extensions, self-#include
instantiates both widths; no intrinsics in the kernels so the 512-bit path compiles
and RUNS everywhere).

Per line: u_j = x_j + x_{23−j}, w_j = −i(x_j − x_{23−j}) (11 vadd + 11 vsub + 11
MULI = shuffle+xor on port 5); P_k = x_0 + Σ_j cos(2πkj/23) u_j (12 accumulators ×
11 rank-1 updates = 132 vector FMAs, 11 of them coefficient-1 adds); R_k = Σ_j
sin(2πkj/23) w_j (121 vector FMAs); X_k = P_k ± R_k (22 add/sub).  All coefficients
REAL (the fold is what makes them real), so interleaved complex is already the right
SIMD layout and there is no cross-lane arithmetic outside MULI and the store tiles.

**Operation count**: 253 FMA + 44 add/sub = **297 vector FP ops per line-group**;
per volume 3·529 lines → at WC=4, 409 chunk calls × 297 = **121.5k vector FP
instructions**.  Floors: node (one 512-bit FMA @ 2.9 GHz) **41.9 µs**; wallaby (two
FMA units @ ~3.9 GHz) ~15.6 µs.  Measured B=1 on wallaby 23.4 µs = 1.50× its floor.
Same yardstick as L23_matrixsimd's header (they quote the identical 121.5k / ~42 µs
figure — same arithmetic, as it must be).

Kernels (fully unrolled, generated by script to avoid index transcription errors):
* `krn_ts` — two sweeps; the 11 distinct cosine magnitudes then the 11 distinct sine
  magnitudes pinned in registers (cos(2π(23−m)/23) = cos(2πm/23) so cosines carry
  their own sign; sine signs are compile-time ±FMA).  Zero coefficient loads.
  Optional variant parks the 12 P accumulators in L1 across the sine sweep.
* `krn_il` — interleaved single-load: each (x_j, x_{23−j}) pair loaded ONCE per line
  (23 vs 46 data loads), both accumulator banks advance together, coefficients as
  FMA memory operands from a pre-splatted j-major table.  This was my experiment the
  rival had not run at L=23 — see "did not work" below.

Passes (structure adopted from L23_matrixsimd ← L17_matrixsimd): per plane, Y
(lanes over z, transposing WC×WC tile store into a 23×24-padded plane buffer), Z
(lanes over ky, transposing store), X over the whole volume (lanes over the 529
contiguous (y,z) pairs, plain strided stores).  Chunk offsets {0,4,8,12,16,19} (w4)
with the last chunk overlapping and rewriting bit-identical values — cheaper than
masking (L17 lesson, not retried).

**X-first for ALL batch sizes** — a deliberate difference from L23_matrixsimd, which
uses X-last below batch 64.  Measured on wallaby at B=1 the X-first pass order wins
by ~5% (23.61 vs 24.92 µs in the same tuner table): X-first writes `out` as dense
per-plane tile stores while the scattered db=1058 stores of the X pass go to the HOT
t1 scratch; X-last does the opposite into a cold `out`.  A single class also removes
the batch-dependent bit-class machinery: the tuner may pick ANY selectable variant at
any batch size because all twelve X-first variants are cmp-verified bit-identical
(full 4-volume outputs, wallaby, md5): kernel form (ts/park/il), width (w4/w2),
NT-copy and pipelining change no bits; only the X-last/X-first pass order changes
the association of the triple sum (the six X-last variants form the other class and
are timed for the record but never picked).

Batch-regime machinery, all adopted with attribution and cmp-verified into the same
bit class:
* cross-volume input prefetch during the plane phase (L17_winograd r2 via
  L17_matrixsimd/L23_matrixsimd), A/B'd at plan time;
* NT-staged planes: Z pass writes a staging plane, streamed to `out` with
  `_mm512_stream_pd` (skips the RFO; L23_matrixsimd's exec_rfn ← L17_matrixsimd);
* cross-volume software pipelining: t1 double-buffered, volume b+1's X chunks
  interleaved into volume b's plane phase at two insertion points per plane
  (L17_matrixsimd r4's exec18 via L23_matrixsimd's exec_p*).

Plan-time tuner (pattern from L17_matrixsimd r3, simplified): times all 18 variants,
picks within the 12-variant X-first class; small cache-resident arena below batch 64,
streaming arena sized to 2.5× this machine's L3 above (L17_winograd r2's lesson —
the streaming regime can prefer a different kernel outright).  Candidates are never
interleaved (512/256-bit licence-transition mis-ranking, L17_matrixsimd r1).
`L23R_VERBOSE=1` prints the table; `L23R_FORCE=<0..17>` pins a variant (that is how
the bit-class matrix was produced).

### What was measured (wallaby, Xeon Gold 6448Y Sapphire Rapids, gcc 11.4, panel flags)

wallaby was intermittently loaded (49 users; process-to-process swings up to 25%
with tiny in-process sd) — numbers are min over ≥3 pinned processes (taskset, cores
12/28/44/60), which was stable to ~1%:

| case | L23_rader | L23_matrixsimd (same conditions) | MKL 2022 |
|---|---|---|---|
| B=1 | **23.42 µs** | 23.56 µs | 143.0 µs |
| B=8 | **29.7 µs/xform** | (not A/B'd) | 143.8 µs |
| B=64 | **28.6 µs/xform** | 27.1 µs | 144.3 µs |
| B=256 | **33.3 µs/xform** | 33.6 µs | (not run) |

rel L2 error 3.8e-16 at every batch tried (1, 3, 4, 8, 64, 100, 256), bitwise
repeatable, and bit-identical to L23_matrixsimd's output (same arithmetic, same
association).  Statistical parity with the rival everywhere within wallaby's noise —
expected, since the arithmetic is identical and both inherit the same L17 scheduling
tricks; the node's clean clock will discriminate the residual scheduling differences
(my always-X-first at B<64, their k-blocked kernel variants).

Clean tuner table at B=1 (one quiet run, w4 unless said): pinned two-sweep X-first
23.61; P-parked 24.06; interleaved 26.10; pinned X-first w2 28.53; pinned X-LAST
23.92–24.92 across runs.  NT planes at B=64: 36.8 vs 30.0 for plain — B=64 (24 MB
in+out) still fits wallaby's 60 MB L3, so NT only forfeits cache hits there.  On the
node (22 MB L3) B=64 is already streaming, so the tuner may flip to NT there — that
is exactly what the plan-time tuner is for.

### What was tried and did NOT work

* **Interleaved single-load kernel (`krn_il`)**: 26.10 vs 23.61 µs at B=1 on wallaby
  (−10%).  Halving the data loads does not pay on a machine with two load ports and
  two FMA units; the 23 live accumulators + 2 temps force gcc to spill P registers
  inside the hot loop, and unlike the two-sweep form the spills sit between
  dependent FMAs.  Left selectable (it is bit-identical) in case the node's 1-FMA
  port balance differs, but I expect the two-sweep pinned kernel there too.
* **Rader-proper realizations of the conv-11 pair**: killed by counting before
  implementation — see the top section.  20-mult Winograd conv-11 ≥ ~300 unfused ops
  vs 242 fused; Karatsuba ~200 vs 121 per conv; FFT-22 route ≈ 2× total.  Do not
  spend a round implementing these; the FMA=add=1-cycle port model has to change
  (e.g. a machine where multiplies are the scarce resource) before they can win.
* **Un-hardened plan-time tuning on a loaded machine**: with 3 timing reps the tuner
  locked 25% mis-picks into whole processes on busy wallaby (a 256-bit variant at
  B=1, or NT at cache-resident batch).  Bumped to 5 reps min-of; the scored node is
  exclusive so this mainly protects development measurements.

### Next

1. **Node numbers first.**  Both L=23 entries are the same arithmetic; the
   interesting node questions are (a) does always-X-first hold at B=1 on 1 MB L2,
   (b) does NT flip on at B=64 given the 22 MB L3, (c) does the 1-FMA port balance
   ever prefer `krn_il`.  All three are tuner-selectable, so the leaderboard run
   itself answers them; the verbose table under `L23R_VERBOSE=1` would answer them
   explicitly if the monitor cares to capture it.
2. **The arithmetic floor is settled** at 297 vector ops/line unless someone finds a
   cyclic-11 convolution under 121 effective fused ops — the corpus says none exists
   (minimal 20 mults, but >130 adds).  I recommend the panel treat further L=23 work
   as scheduling-only and consider whether two identical-arithmetic entries are worth
   two slots; the differentiated experiment would be a genuinely different geometry
   (L=13: p−1 = 12 = 4·3, partially lucky — one free ± split then a cyclic-3, which
   DOES have a cheap module; that would interpolate between 17-lucky and 23-unlucky
   and complete the answer this entry started).
3. If a scheduling round is still wanted: software-pipeline Y of plane x+1 into Z of
   plane x (smooths the port-5 shuffle bursts of the tile stores), and try NT stores
   on the X pass's t1 writes at streaming batch.
